# Product Requirements Document (PRD): Multi-Browser Tree Backup Utility

## 1. Executive Summary

### 1.1 Overview
The Multi-Browser Tree Backup Utility is a desktop background application designed to periodically extract, normalize, and back up browser state structures—including workspaces, spaces, folders, tab groups/stacks, pinned tabs, and active tabs—across various modern browsers into a unified hierarchical tree format.

### 1.2 Problem Statement
Standard browser extension APIs (e.g., `chrome.tabs`, `chrome.tabGroups`) cannot access proprietary layout layers such as Arc’s sidebar spaces/folders or Vivaldi’s nested tab stacks. Furthermore, browsers hold live state in memory and place file locks on profile databases/files during active sessions, preventing direct in-place queries.

### 1.3 Solution Approach
Since real-time synchronization is not required, a desktop background daemon runs on a configurable interval (e.g., every 5–15 minutes). It safely copies local profile files to an isolated cache directory, decompresses/parses browser-specific data formats, maps them to a unified Adjacency List schema, and performs delta upserts into an external database (SQLite / PostgreSQL).

## 2. System Architecture & Data Model

### 2.1 Entity Definitions
The unified hierarchy normalizes disparate browser concepts into 5 core entity types:

| Entity | Description & Scope | Key Attributes |
| :--- | :--- | :--- |
| **Root** | Top-level node representing a specific browser installation/profile on a host device. | `id`, `browser_name` (e.g., Chrome, Arc), `os_type` (macOS, Windows, Linux), `profile_name` |
| **Window** | An OS-level browser window instance containing one or more workspaces. | `id`, `parent_id` (points to Root), `title`, `sort_order` |
| **Workspace** | A named workspace, space, or profile context within a window (or a default space for browsers without native workspaces). | `id`, `parent_id` (points to Window), `title`, `sort_order` |
| **Folder** | A container grouping tabs or nested folders (maps to Tab Groups in Chrome, Tab Stacks in Vivaldi, Folders in Arc/Zen). | `id`, `parent_id` (points to Workspace or parent Folder), `title`, `sort_order` |
| **Split View** | A non-nestable container for Arc split views and Vivaldi tiled tabs rendered together; it cannot contain folders. | `id`, `parent_id`, `title`, `sort_order` |
| **Tab** | A leaf node representing an individual web page (regular or pinned). | `id`, `parent_id` (points to Workspace or Folder), `title`, `url`, `node_type` (`tab` / `pinned_tab`), `sort_order` |

### 2.2 Hierarchical Relationship Model

```
[Root] (Browser Brand + OS Type + Profile)
 └── [Window] (Window 1, Window 2, ...)
      └── [Workspace / Space] (Personal, Work, Default, ...)
           ├── [Folder / Tab Stack] (Category A)
           │    ├── [Sub-Folder]
           │    │    └── [Tab / Pinned Tab]
           │    └── [Tab / Pinned Tab]
           ├── [Folder / Tab Stack] (Category B)
           │    └── [Tab / Pinned Tab]
           └── [Tab / Pinned Tab] (Direct un-grouped tabs)
```

#### Structural Relationship Rules:
- **`Root` $\rightarrow$ `Window`**: 1-to-many relationship (one browser profile can span multiple windows).
- **`Window` $\rightarrow$ `Workspace`**: 1-to-many relationship (one window contains one or more workspaces/spaces).
- **`Workspace` $\rightarrow$ `Folder` / `Tab`**: Workspaces can directly contain un-grouped tabs or top-level folders.
- **`Folder` $\rightarrow$ `Sub-Folder` / `Tab`**: Folders can be nested recursively to arbitrary depth, containing sub-folders and/or tabs.

### 2.3 Database Schema (PostgreSQL / SQLite)
An Adjacency List model is used to support flat tabs, grouped stacks, and arbitrarily nested folders in a single relational table.

```sql
CREATE TABLE browser_trees (
    id VARCHAR(255) PRIMARY KEY,          -- Unique ID generated by the browser or deterministic hash
    browser_name VARCHAR(50) NOT NULL,    -- 'chrome', 'vivaldi', 'arc', 'zen', etc.
    os_type VARCHAR(50) NOT NULL,         -- 'macos', 'windows', 'linux'
    profile_name VARCHAR(100) NOT NULL,   -- e.g., 'Default', 'Profile 1'
    node_type VARCHAR(50) NOT NULL,       -- 'root', 'window', 'workspace', 'folder', 'split_view', 'tab', 'pinned_tab'
    title TEXT,                           -- Title of window, workspace, folder, or tab
    url TEXT,                             -- NULL for containers; URL string for tabs
    parent_id VARCHAR(255),               -- Recursive pointer to the containing entity (NULL for Root)
    sort_order INT NOT NULL,              -- Visual ordering index inside parent container
    snapshot_time TIMESTAMP NOT NULL      -- Timestamp identifying the synchronization batch
);

CREATE INDEX idx_browser_parent ON browser_trees (browser_name, parent_id);
```

## 3. Browser Parsing Specifications

| Browser | Target File Path | Format | Data Extraction Strategy |
| :--- | :--- | :--- | :--- |
| **Google Chrome** | `.../User Data/<Profile>/Preferences` | JSON | Parse standard JSON. Extract `tab_groups` object to obtain group names, IDs, visual properties, and colors. |
| **Vivaldi** | `.../Vivaldi/User Data/<Profile>/Preferences` & Sessions log | JSON / Sessions Log | Parse JSON under `vivaldi` &rarr; `workspaces` and `vivaldi` &rarr; `tab_groups`. Extract tabs from adjacent Sessions log where `extData` JSON string maps tabs back to group IDs. |
| **Arc Browser** | `.../Arc/StorableSidebar.json` | JSON | Parse standard JSON containing complete workspace, folder, and tab layout explicitly mapping tree objects without needing live memory queries. |
| **Zen Browser** | `.../zen/Profiles/<Profile>/sessionstore.jsonlz4` | Mozilla LZ4 (`jsonlz4`) | 1. Strip the custom 8-byte Mozilla magic header (`mozLz40\0`).<br>2. Decompress payload via standard LZ4 algorithm to obtain JSON string.<br>3. Traverse active structural arrays to extract folders, workspaces, and tab trees. |
| **Firefox** | `.../Firefox/Profiles/<Profile>/sessionstore-backups/recovery.jsonlz4` | Mozilla LZ4 (`jsonlz4`) | Prefer the running-session recovery snapshot; preserve window order, pins, tab-group membership, split-view collections, and tab order. |

## 4. Implementation Workflow & Processing Pipeline

### 4.1 Pipeline Overview

```
[Timer Loop (5-15 min)] ──> [Safe File Copy] ──> [Parser Engines] ──> [Diff & Upsert DB]
```

### 4.2 Step-by-Step Execution

#### Step 1: Background Daemon Initialization
- Build daemon using a system-level runtime (Node.js/TypeScript, Go, Rust, or Python) supporting efficient file I/O and DB operations.
- Set up a scheduled interval loop (default: every 10 minutes, configurable between 5–15 minutes).

#### Step 2: Safe Snapshot Worker
- Identify active browser profiles and verify file existence at target OS paths.
- Copy locked/live files to a temporary staging workspace (e.g., `~/.browser_sync_cache/tmp/`) before reading to prevent read locks and race conditions with browser write cycles.

#### Step 3: Parsing & Normalization Engines
- Dispatch staging files to their respective browser parser modules.
- Decompress proprietary streams (e.g., `jsonlz4` for Zen/Firefox).
- Transform browser-specific data models into standardized tree node objects conforming to the database schema.

#### Step 4: Database Delta Check & Upsert
- **Deterministic ID Generation**: If a browser entity lacks a native persistent ID, compute a deterministic hash:
  $$\text{ID} = \text{hash}(\text{browser} + \text{url} + \text{parent\_folder\_title} + \text{profile})$$
- **Upsert Strategy**: Execute `INSERT ... ON CONFLICT (id) DO UPDATE` queries to update modified titles, URLs, sort orders, and parent associations.
- **Orphan Pruning**: Optionally delete or archive records whose `parent_id` references nodes that no longer exist in the latest snapshot batch.

## 5. Non-Functional Requirements & Risk Mitigation

### 5.1 File Corruption Prevention
- **Strict Read-Only Cache Policy**: Never attempt to write or mutate active browser profile files directly. Always perform parsing operations exclusively on isolated temporary copies.

### 5.2 Schema Evolution & Fault Isolation
- Wrap each browser-specific parser in independent error boundaries (`try/catch`).
- A parser failure or schema change in one browser (e.g., Chrome update) must not block or crash synchronization for other supported browsers (e.g., Arc, Zen, Vivaldi).

### 5.3 Operating System Permissions & Paths
- Ensure application handles standard OS file paths and permissions:
  - **macOS**: `~/Library/Application Support/...`
  - **Windows**: `%APPDATA%/...` and `%LOCALAPPDATA%/...`
  - **Linux**: `~/.config/...` and `~/.mozilla/...`
- Request or verify requisite disk read permissions during setup.

## 6. Technical Stack & Implementation Options

Potential runtimes for the background worker:
- **Rust / Go**: Low resource footprint, fast LZ4 decompression, single binary deployment.
- **Node.js / TypeScript**: Rich ecosystem for SQLite/PostgreSQL ORMs and JSON handling.
- **Python**: Rapid prototyping with built-in `lz4` and `sqlite3` libraries.
